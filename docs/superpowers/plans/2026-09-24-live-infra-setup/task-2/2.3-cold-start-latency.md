# Subtask 2.3: Explain (or fix) scanner cold-start latency, then set a measured deadline

Timebox: 90 min. Precondition: Subtask 2.2 is done (`zcash-up.ts` exits 0; doctor zcash and scanner PASS). The previous subtask's notes carry one measured "wallet sync ready → scanner ready" duration.

## Background

Before the socket-path fix, runs appeared to take 300–500+ s between `ths` reporting `wallet_sync: ready` and the scanner's `/v1/snapshot` reporting `complete:true, health:"ready"`, although `tip.height == scanned.height == 104` (birthday equals tip, so there is nothing to scan). Some of that was very likely the ENOENT misreading, because clients could never connect by the absolute path. This subtask establishes the real number. The lifecycle worker retries with capped backoff up to 32 s per attempt (`services/scanner/src/daemon.rs`).

## Steps

1. **Measure a true cold start of the scanner only.** Keep `ths` running. Stop `serve` (PID in `SCANNER_DIR/serve.pid`, cmdline-checked), then run `ZCASH_UP_TRACE=1 node --experimental-strip-types scripts/live-infra/zcash-up.ts > .runtime/live/diag/2.3-cold-<n>.log 2>&1`. Compute seconds from `step6: starting` to `step6: scanner ready`. Do this 2 times.
2. **Decision:**
   - If both runs are ≤ 60 s, the old latency was the ENOENT artifact. Set the Step 6 deadline to `max(180_000, 3 × worst observed)` and replace the existing comment with one citing the measured values and the date. Done.
   - If either run is > 60 s, continue with step 3.
3. **Find the per-attempt failure.** Add temporary `eprintln!` in the lifecycle-worker retry path in `services/scanner/src/daemon.rs`. Print only the error kind or message, and never keys, UFVKs or addresses. Rebuild with `cargo build --locked --release --manifest-path services/scanner/Cargo.toml`, repeat the step 1 measurement, and read only `grep -n 'lifecycle\|attempt\|error' SCANNER_DIR/serve.log | tail -n 40`. Identify the failing call (candidates: lightwalletd `GetLightdInfo` or consensus check, a tree-state fetch, the RPC, or the backoff schedule itself).
4. **Revert the `eprintln!` instrumentation completely** (`git diff services/scanner` must show no residual debug lines relative to the pre-subtask state; record `git diff --stat services/scanner` before and after).
5. If the cause is an initial backoff that is unnecessarily large and the fix is small and local, propose it in the report. **Do not change scanner retry semantics without the orchestrator asking the user**, because the scanner is Task 3 code with its own tests. Otherwise set the deadline to `max(180_000, 3 × worst observed)`, with a comment that names the cause and the measurement.
6. Append any `ths` observation to the DX backlog (`~/.hermes/skills/software-development/zakura-regtest/references/ths-dx-backlog.md`), for example "`wallet_sync: ready` precedes lightwalletd gRPC readiness by N s".
7. Re-run `zcash-up.ts` once more (it must exit 0), and check that the doctor rows are still PASS.

## Verify

- The report contains every measured duration and the chosen deadline.
- `git diff --stat services/scanner` is identical to its state before this subtask.
- `npx vitest run tests/unit/live-infra-zcash.test.ts` passes. `SSF_STRICT_LIVE=1 npm run infra:doctor | grep -E '^(zcash|scanner) '` shows two PASS lines.
