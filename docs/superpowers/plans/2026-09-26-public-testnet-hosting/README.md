# Public testnet hosting implementation plan (index)

> For agentic workers: REQUIRED SUB-SKILL: superpowers:subagent-driven-development. Each `N.M` subtask is owned by exactly one fresh subagent. The orchestrator (a fresh top-level session) dispatches, re-verifies, and ledgers. Children cannot delegate. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Host one seller's Sovereign Storefront publicly on Zcash testnet. Any website can embed a Buy button for the seller's products. A buyer pays shielded TAZ from a separate testnet wallet, the order and delivery key travel over Logos Delivery (Waku) encrypted, signed messaging, and the encrypted file is served from Logos Storage testnet nodes the seller operates. T01 acceptance uses a disposable, explicitly funded automation wallet, not the user's personal wallet.

**Architecture:** Keep the proven live-L architecture: seller service, a view-only Rust scanner, Waku messaging and a Logos Storage origin plus replica. Swap regtest for Zcash testnet (public TLS lightwalletd `testnet.zec.rocks`). Raise the payload cap to 8 MiB. Add a multi-product catalogue and an embed surface (`embed.js` plus a popup checkout on the storefront origin). The main stack runs on a Raspberry Pi (aarch64, 16 GB RAM, 100 GB disk) as Docker Compose services. The Logos storage replica B runs on a separate Hetzner server, `ssf-replica` (x86_64, 2 vCPU, 4 GB, 38 GB, Ubuntu 26.04, Helsinki), joined to the tailnet. A replicates to B over Tailscale; the seller checks B through a small replica agent reachable only on the tailnet. Cloudflare Tunnel (`cloudflared`, outbound-only, free) publishes `https://store.agentmascot.app` (seller) and `wss://wss.agentmascot.app` (our own Logos delivery node, the guaranteed browser entry peer). The demo embedder is a Cloudflare Pages site. The admin API is never tunnelled; the operator reaches it over Tailscale SSH. Spending keys never touch the Pi.

**Tech stack:** Node 22 and TypeScript (seller, browser, Vite), Rust (`services/scanner`, `zakura-client-backend =0.1.0-rc5`), `@waku/sdk 0.0.36`, `logosctl 0.2.3` with `storage_module 2.1.2` on the `logos.test` network, Docker Compose (arm64 images), Cloudflare Tunnel and Pages, Tailscale SSH, Playwright. [Cua Driver (trycua/cua)](https://github.com/trycua/cua) is a separate operator-side GUI validation tool for T01, not an application or deployment dependency.

**Spec:** `docs/superpowers/specs/2026-09-23-live-mvp-integration-design.md` §2 "T — public-testnet qualification", plus `docs/mvp-design.md`. This plan implements T and the hosting and embed layer that T omitted. It also lifts the design's "Public Logos deployment, useful-size file support" exclusion, but only for testnet.

**2026-09-29 VPS addendum:** At the user's direction, the public stack, independent checker, fresh buyer wallet, and Playwright runner now operate on `ssf-replica`. A fresh two-payment T01 produced a validated report with eight of eight stages PASS; see [demo results](../../../demo-results.md). The user waived migration and archival of the earlier zingo buyer wallet; its former host is offline, and no backup or deletion was performed.

## Decisions (answered at G1)

- **D1 = b.** Browser keeps signed, encrypted Waku (Logos Delivery wire protocol) via `@waku/sdk`, plus our own Logos `delivery_module` node on the Pi with a WebSocket listener, published as `wss://wss.agentmascot.app` through the Tunnel and pinned first in `WAKU_BOOTSTRAP_PEERS`. Fallback if spike 1.3 shows `delivery_module` cannot serve light-push/filter over WS on aarch64: public peers only (D1=a), recorded at G2.
- **D2 = a.** `https://testnet.zec.rocks:443`. lightwalletd can withhold blocks (liveness) but cannot forge notes.
- **D3 = a.** `embed.js` Buy button opens a popup checkout on `store.agentmascot.app`; purchases live in first-party storage there.
- **D4 = a.** Single seller instance plus a self-host kit.
- **D5 = a.** 8 MiB single-shot AES-GCM.
- **D6 = b.** Docker Compose. `logosctl` runs extracted (`--appimage-extract`) inside the container because FUSE is unavailable there. Images are built for `linux/arm64` on the aarch64 laptop and loaded on the Pi (`docker save | ssh pi docker load`), so the Pi never compiles Rust.
- **D7 = second host.** Replica B runs on `ssf-replica` (Hetzner, x86_64). Files stay downloadable when the Pi's Logos node is down, and B holds an off-site copy of every published ciphertext. It is x86_64, so the Logos image is built per architecture (the x86_64 `logosctl` 0.2.3 AppImage is published with sha256). It also serves as the x86 fallback for the messaging node if spike 1.3 shows the Logos delivery module cannot serve browsers on aarch64 (nwaku is x86-only).
- **D8 = b.** Minimum 3 confirmations, testnet only, shown in the UI ("testnet: 3 confirmations"). `real-demo` keeps its 10 floor.

## CUA scope and qualification for T01

Use [trycua/cua](https://github.com/trycua/cua) only for **optional additional GUI coverage** of the third-party embed → storefront popup → My purchases → recovered download. Task 5.2's primary repeatable path is Playwright against a persistent, dedicated Chromium profile plus the testnet buyer sender `ssf-buyer-sender` (replaces zingo-cli; see [docs/superpowers/plans/2026-09-29-zakura-buyer-sender.md](../2026-09-29-zakura-buyer-sender.md)). CUA is not a wallet, funding source, scanner, Waku transport or payment oracle. The real CLI payment is sent by the isolated automation wallet only after the application invoice and decoded QR are validated; release still depends exclusively on the view-only seller scanner. Never grant CUA access to the user's personal wallet or place it in the buyer app, seller service, Pi Compose stack or `ssf-replica`.

Before any optional CUA run, follow the [Driver install requirements](https://cua.ai/docs/how-to-guides/driver/install), [platform support](https://cua.ai/docs/reference/cua-driver/platform-support), [permission modes](https://cua.ai/docs/reference/cua-driver/permission-modes) and [browser-profile lifetimes](https://cua.ai/docs/reference/cua-driver/browser-profile-attachment). Document the exact Driver release, desktop/architecture, browser, profile strategy and `cua-driver doctor`/`status` results. The documented Linux Driver needs an x86_64 **graphical** session with AT-SPI; the aarch64 laptop/Pi are not assumed compatible. The user later directed the isolated buyer wallet and Playwright runner onto the VPS. Do not provision a paid Fleet, install a driver, or attach to the user's everyday browser without the required grant. If no supported runtime is available, record CUA `NOT_RUN` with the reason and continue the automated Playwright + CLI-wallet T01; never call it a CUA pass.

When CUA is separately qualified, use a reviewed bounded capability manifest for the embedder and storefront origins and a dedicated browser profile; never unrestricted agent access or native wallet control. Run `cua-driver telemetry disable`, verify with `cua-driver telemetry status --json`, and leave trajectory recording off before opening sensitive screens. A Driver-owned disposable profile can disappear at session end; the primary Playwright flow proves browser-process restart with one persistent profile and separately proves backup import in a fresh context **before spending**. Closing a CUA session alone is not that test. Neither prompts nor saved screenshots/logs may contain wallet seeds, buyer credentials, QR/payment URIs, invoice addresses or memos.
