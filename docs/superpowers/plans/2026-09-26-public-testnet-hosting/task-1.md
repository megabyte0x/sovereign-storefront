# Task 1: Qualification spikes (parallel, read-mostly, throwaway code under `spikes/`)

Each spike answers one go/no-go question with command evidence. No production files. Each spike ends with a verdict row for G2. They run in parallel because their Owns sets are disjoint directories.

## 1.1 Scanner against public testnet lightwalletd

- **Owns:** `spikes/scanner-testnet/**`, report only. Timebox 2 h.
- **Question:** Can the pinned `zakura-client-backend =0.1.0-rc5` scan Orchard notes on Zcash testnet through `https://testnet.zec.rocks:443`, and which code paths hardcode regtest?
- [ ] Inventory every regtest assumption: `grep -rn "regtest\|LocalNetwork\|local_network" services/scanner/src`. Classify each hit as (config gate | params type | UFVK decode | test-only). Known hits: `config.rs` `open_runtime_paths` (network check), `decode_regtest_orchard_ufvk`, `ActivationHeights::local_network`, `allocate.rs:17-24`, `wallet.rs` test params.
- [ ] Check whether the backend exposes `zcash_protocol::consensus::Network::TestNetwork` for `Parameters` usage, or whether `LocalNetwork` with testnet activation heights is required: `cargo tree -p zcash_protocol` and read the `consensus` module. Record which one to use.
- [ ] Probe TLS lightwalletd with the scanner's own transport feature (`lightwalletd-tonic-tls-webpki-roots`): a spike bin calling `GetLightdInfo` and `GetTreeState(height=birthday)`. Print chain name, block height and consensus branch id.
- [ ] With a throwaway testnet UFVK (generated by the spike via `zcash_keys` test seed; NOT the seller's), import at a recent birthday and sync 1,000 blocks. Record wall time and DB size.
- **Verdict:** `GO` (params choice, sync rate, estimated full-sync time from the seller birthday) or `NO-GO` (the exact failure). This feeds D2.

## 1.2 Logos Storage in containers on aarch64

- **Owns:** `spikes/logos-container/**`. Timebox 2 h. Runs on the aarch64 laptop (same arch as the Pi).
- **Question:** Can `logosctl 0.2.3` + `storage_module 2.1.2` run in containers without FUSE (arm64 on the laptop, amd64 on `ssf-replica`), on `network: "logos.test"`, and replicate an 8 MiB file across hosts over Tailscale?
- [ ] Dockerfile (Debian bookworm-slim arm64): copy the cached verified aarch64 archive that `scripts/live-infra/logos-up.ts` already uses (do not download a new one); run `logosctl-aarch64.AppImage --appimage-extract` at build time; entrypoint is the extracted `squashfs-root/usr/bin/logosctl` (check the real path) with `--config-dir /data`.
- [ ] Two containers on one Compose network; A `listen-port` 8091; B connects to A by `/ip4/<A container IP or DNS-resolved>/tcp/8091/p2p/<peerA>` (the L lesson: `connect json:[]` is not enough).
- [ ] Upload 1 MiB and 8 MiB on A, download on B, compare sha256, record timings. Stop A, re-read from B.
- [ ] Cross-host: build the amd64 variant from the x86_64 archive (sha256 `baa6e245…d851`, AppImage `3ee96869…dd1e`, https://docs.logos.co/run-a-node) directly on `ssf-replica` (`tailscale ssh root@ssf-replica`; install Docker there first, see 4.1b). Laptop node A publishes 8091/tcp on its Tailscale IP only; B on `ssf-replica` connects by `/ip4/<laptop-tailscale-ip>/tcp/8091/p2p/<peerA>`. Repeat the 8 MiB sha256 check and the A-stopped read. Record throughput over the tailnet (the relay path, `relay "hel"`, may be slow; note whether a direct connection forms).
- [ ] Record: image size, RAM per node, whether `watch` events work in the container, and any `storage_module` install step that needs network at runtime (should be baked into the image).
- **Verdict:** GO with the Dockerfile, or NO-GO with the exact error (fallback: run Logos natively on the Pi (FUSE AppImage, user service) and the rest in Compose; D6 partial).

## 1.3 Messaging: own Logos delivery node as browser entry peer (D1=b)

- **Owns:** `spikes/messaging-public/**`. Timebox 2.5 h. Runs on the aarch64 laptop.
- **Question:** Can the Logos `delivery_module 0.2.1`, loaded through the aarch64 `logosctl`, run a node that serves light-push and filter to browsers over WebSocket, on the same network (cluster/shards) our `@waku/sdk 0.0.36` code uses (`DefaultNetworkConfig`, `src/adapters/waku.ts:94,150`)?
- [ ] Install `delivery_module 0.2.1` (https://docs.logos.co/run-a-node step 7). Try an `entryLayer` that serves light-push/filter (not `kernel`, which omits send/subscribe). Enable a WebSocket listener on 127.0.0.1:8000 if the config supports it; record the exact config keys that worked.
- [ ] Record `getNodeInfo MyMultiaddresses` and the cluster/shards it joins; compare with `DefaultNetworkConfig`.
- [ ] Expose it with a quick tunnel (`cloudflared tunnel --url http://127.0.0.1:8000`, random `trycloudflare.com` hostname) and check that a headless Chromium `@waku/sdk` light node dials `/dns4/<host>/tcp/443/wss/p2p/<peer>`, light-pushes 50 signed messages, and filters them back. Record success rate and p95 latency. A quick tunnel is test-only.
- [ ] Baseline: the same round trip against public peers from `scripts/live-infra/waku-peers.ts`, 10 runs over 30 min.
- [ ] If `delivery_module` cannot do WS service on aarch64: try the nwaku source build only if under 30 min remain in the timebox; otherwise stop.
- **Verdict:** D1=b GO (config + numbers) or fall back to D1=a (public peers only) with evidence. Also record that Logos Chat (`logos-chat`) is Rust linking native `liblogosdelivery` with no browser binding, so it cannot serve embedded web checkout.

## 1.4 Embed and storage-partition behaviour

- **Owns:** `spikes/embed/**`. Timebox 90 min.
- **Question:** Does a purchase stored in IndexedDB survive the embed model we pick?
- [ ] Two local origins (`http://a.localhost:5001` embedder, `http://s.localhost:5002` storefront). Playwright Chromium and WebKit: (i) iframe writes IDB, then read at the top-level storefront; (ii) popup opened from the embedder writes IDB, then read at the top level; (iii) `window.opener.postMessage` result back to the embedder.
- **Verdict:** a table of browser × model × visible-at-top-level. Expected: iframe is partitioned and the popup is first-party. This confirms or overturns D3.
